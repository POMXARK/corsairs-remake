# Как читается логика оригинала

Исходный код «Корсаров» (Akella, 2000) не опубликован. Его не восстановить в виде, в каком он был написан: имена переменных и функций, комментарии и структура файлов при компиляции пропали. Но машинный код DLL из `MODULES/` можно **декомпилировать**. Получается псевдо-C: логика та же, имена вида `FUN_10002a80`, `param_1`, `local_98`, константы — адреса `_DAT_1000c200`. По нему видно, *что* делает игра. Переписывать его мы не стали: правила оригинала переносятся в конвертеры и скрипты своими словами.

Результат декомпиляции — код Akella, в git он не кладётся. Лежит только локально в `$W/ref/pdm-decomp`. В репозиторий идут скрипты, которые его получают, и выводы о форматах и правилах (`pdm-formats.md`, `original-vs-remake.md`).

## Инструменты

- **Ghidra 12.1.4** (NSA, открытая, Apache 2.0) — дизассемблер и декомпилятор. Распакована в `$W/tools/ghidra_12.1.4_PUBLIC`. Ей нужен JDK 21+, у нас `/usr/lib/jvm/jdk-24.0.1-oracle-x64`.
- [`tools/ghidra/decompile.sh`](../tools/ghidra/decompile.sh) — запускает Ghidra без окна (`analyzeHeadless`): импорт DLL, автоанализ, потом скрипт.
- [`tools/ghidra/DumpDecomp.java`](../tools/ghidra/DumpDecomp.java) — скрипт Ghidra. Выгружает C каждой функции и все строки DLL.
- [`tools/pe_const.py`](../tools/pe_const.py) — читает константу из DLL по адресу, который показывает Ghidra.

## Шаг 1. Выгрузить все DLL

```bash
W=/media/roman/383be9ee-c114-4bf8-8956-66b985661cb4/home/remake-linux
PDM=/media/roman/383be9ee-c114-4bf8-8956-66b985661cb4/home/Корсары
JAVA_HOME=/usr/lib/jvm/jdk-24.0.1-oracle-x64 GHIDRA=$W/tools/ghidra_12.1.4_PUBLIC \
  corsairs-remake/tools/ghidra/decompile.sh $W/ref/pdm-decomp $PDM/MODULES/*.dll
```

Для каждой DLL получаются три файла:

- `<dll>.c` — все функции; перед каждой строка `// <адрес> <имя>`;
- `<dll>.strings.txt` — строки с адресами;
- `<dll>.log` — лог анализа.

104 модуля обрабатываются около 40 минут, запускать в фоне.

Функции, до которых анализ не добрался (их зовут только через виртуальную таблицу), передаются адресами в `ENTRIES`. Адреса берутся из таблицы в `.rdata`, на которую ссылается конструктор:

```bash
ENTRIES="100032e0 10003f10 100042f0 10002130" JAVA_HOME=… GHIDRA=… \
  corsairs-remake/tools/ghidra/decompile.sh $W/ref/pdm-decomp $PDM/MODULES/zombi.dll
```

## Шаг 2. Найти нужную логику

Порядок поиска на примере вопроса «почему в оригинале герой не заходит в стены».

1. **Выбрать модуль по имени.** Персонаж на суше — `MAN.dll`, город — `land_sector.dll`, камера — `CAMERA_FOLLOW.dll`, диалоги — `DIALOG_TERMINAL.dll`, квесты — `QUEST_EDITOR.dll`.
2. **Найти зацепки в строках:** имена анимаций, файлов, ключей ini.
   ```bash
   cd $W/ref/pdm-decomp
   grep -v "R60\|Heap\|KERNEL" MAN.dll.strings.txt | tail -80   # walk, turn_left, land_sector, cam_city…
   ```
3. **Найти по строке функцию.** Ищется адрес строки (`grep -n "1000d0f0" MAN.dll.c`) или числа, характерные для задачи. Ghidra пишет короткие float прямо в код (`0.3`), длинные — как `_DAT_…` или hex (`0x3e99999a` = 0.3f).
   ```bash
   grep -o "[0-9]*\.[0-9]\+" MAN.dll.c | sort | uniq -c | sort -rn | head
   grep -n "0\.3\b" MAN.dll.c
   ```
4. **Прочитать функцию и достать её константы из DLL:**
   ```bash
   python3 corsairs-remake/tools/pe_const.py $PDM/MODULES/MAN.dll 1000c1e0 1000c1e8 1000c1f0 1000c1f8 1000c200
   ```
   Когда в коде стоит `(float10)_DAT_…`, константа обычно хранится как `double`.
5. **Понять, к какому объекту идут вызовы.** Например, `(**(code **)(**(int **)(param_1 + 0x22460) + 0x80))()` — вызов метода по смещению 0x80 у объекта из поля `0x22460`. Откуда взялось поле, видно по присваиванию: `grep -n "0x22460" MAN.dll.c`.

## Что так уже найдено

- **Стены (`MAN.dll`, функция около строки 1010 выгрузки).** Каждый кадр персонаж трассирует пять лучей-«усов» на высоте 0.3 м над полом: вперёд 0.285 м, назад 0.275 м, под 45° 0.395 м, вбок 0.375 м. Трасса идёт через службу геометрии ядра (вызов `+0x80`), по модели локации. Если задет один ус, герой поворачивает и скользит вдоль стены. Если задеты оба передних — останавливается. Значит, в оригинале патч — только пол, а стены держит модель. В Storm Engine персонаж ходит только по патчу, поэтому `tools/pdm_world.py` заранее вырезает из пола всё, что ближе 0.3–0.375 м к модели на высоте от 0.3 м.
- **Горожане (`land_sector.dll`, `zombi.dll`).** `land_sector` создаёт по объекту `zombi` на каждого горожанина. Класс модели берётся из `anim_types.idf`:
  - бродят классы 3, 9, 10, но не в таверне (тип локации 3) и не в резиденции (6);
  - стража (класс 2) и пьяницы (5–7) стоят;
  - бродящему передаются координаты всех точек типа 3 (сообщение `0x2381`).

  `zombi` выбирает случайную точку, видимую трассой, и не ту, где стоит. Точка считается достигнутой на расстоянии меньше 2,0 единицы (4,6 м). Затем он стоит `rand % 10 + 3` действий. В конце каждого действия:
  - в 4 случаях из 5 играет `stand_calm`;
  - иначе один из `do_some1..3`.

  При встрече с соседом поворачивается к нему и играет `hi_1`/`hi_2`, в разговоре — `talk_1..4`. Порядок действий (индексы в таблице на 0x28 байт):
  - 0 `stand_atack`;
  - 1 `stand_calm`;
  - 2–4 `start_walk`, `cyrcle_walk`, `finish_walk`;
  - 24–26 `do_some1..3`;
  - 27–28 `hi_1..2`;
  - 29–32 `talk_1..4`.

  Перенесено в `Town_Wander` (`program/town.c`) и веса idle в `tools/pdm_character.py`.
- **Скорость анимации.** Нарезка действий лежит в данных: `WORLDS/CHARACTERS/*.idf`, поля `start_action`, `end_action`, `speed` у каждого действия. `MAN.dll` читает их в таблицу по 0x28 байт (выгрузка, строка около 1837). Частоты кадров нет ни в данных, ни среди констант `MAN.dll`: там только углы (2π/100, π/2, π/4) и длины «усов». Значит, кадр продвигает ядро, а его код не найден. Мы берём 10 кадров в секунду (`FPS` в `tools/pdm_character.py`). При ней жесты выглядят естественно, а ходьба героя (`cyrcle_walk`, 20 кадров на два шага, `speed 30`) даёт 60 шагов в минуту и 0,7 м/с. Это вдвое медленнее человека (около 120 шагов и 1,4 м/с), поэтому ходьба и бег ускорены в 2 раза (`WALK_RATE`, `RUN_RATE`, помечены ours).
- **Условия и действия сюжета.** Таблицы указателей в `.data` DLL читались напрямую: строки короче 5 символов (например, `KILL`) в выгрузку Ghidra не попадают. Подробно — в [original-vs-remake.md](original-vs-remake.md).
- **Верфь (`TOWN.dll`).** Функцию, которая читает `[ShipYard]` и создаёт кнопки и узлы, Ghidra сама не находит: выгружать с `ENTRIES="10003d10"`. Кнопки получают номера: `lb_Exit` 0, `lb_Sell` 1, `lb_Repair` 2, `lb_Buy` 3, `lb_Upgrade` 4 (Refit), `lb_LeftHull`/`lb_RightHull` 5/6, `lb_LeftRig`/`lb_RightRig` 7/8, `lb_RepairAll` 0x10. Портрет корабля — `GOODS\SHIPS\<id>_lg.tga`, орудия — `GOODS\GOODS\<файл>64.tga`. Режимы экрана (`FUN_100056c0`): 0 — свои корабли, 1 — замена корпуса (проверки золота и ранга, строки «не хватает…»), 2 — обшивка («Sheathe cost %d gold»). Цены и проценты считаются на x87 (`__ftol`, `FUN_10005310`), их константы читать `pe_const.py`. **Обшивка корпуса (кнопка 4) в оригинале не работает:** таблица переходов обработчика верфи (`TOWN.dll 0x1000702d`, таблица `0x100076cc`) для номера 4 ведёт на общий выход `0x100076b9` (только ставит флаг «обработано»), а режим окна (`+0x1400c`, `FUN_100056c0`) принимает лишь 0 и 1 — значение 2 с текстом «Sheathe cost %d gold» нигде не выставляется. Это недоделанный код Akella: игроку обшивка недоступна, кнопка скрыта (`Screen_ShipyardHide`), в ремейке ничего делать не нужно. Не перенесено: формулы ремонта и продажи.
- **Форматы файлов** (`.cff`, `.mtx`, `.loc`, диалоги) — в [pdm-formats.md](pdm-formats.md).

## Ограничения

- Имён нет. Смысл полей (`param_1 + 0x22c7c` — скорость, `iVar4 + 0x150` — угол) выводится из того, как они используются.
- Вызовы между DLL идут через виртуальные таблицы ядра (`CORE.dll`), поэтому метод по смещению приходится сопоставлять вручную.
- Ghidra иногда путает аргументы на стеке x87: последовательность вызовов надёжнее отдельных переменных.

## Верфь: что не нашли (тупики)

- Предел класса (`this+0x13ff0`) найден: пишется в `0x10004d50`, формула `6 − (ранг − 1) / 2`, не меньше 1; ранг — поле героя `+0x1cc` (указатель `0x1001f548` ставится в `0x10008656`, деньги — `+0x1d4`). Раньше пропустили, потому что искали запись по `0x13ff0` только в конструкторе. Использование: проверка при выборе типа `0x10005914` (отказ, если предел больше номера класса), строка «до %d класса». Фильтр списка типов («Класс 5/6» на скриншоте оригинала) не найден.
- Поле героя `+0x3d8` в формуле цены (зажато [−30;30]) — это репутация героя (CORE.dll, атрибут `Reputation`); в ремейке `PlayerCard.reputation` (`Trade_Rep`).
- Навык № 2 в формуле цены — Торговля (порядок `skills.idf`: sailing, repair, commerce, …).
- `ref/sd-teho-public` — исходники другой игры, только справка, не копировать.

## Верфь: цена ремонта и продажи (TOWN.dll)

- `FUN_10005310` (`0x10005310…0x100055fc`): `[esi+0x177b4]` — цена продажи своего корабля; `0x177ac`/`0x177b0` — цена ремонта корпуса/оснастки до выбранной доли (`0x1779c`/`0x177a0`), `0x177b8`/`0x177bc` — до 100%; `0x177a4`/`0x177a8` — текущие проценты корпуса/оснастки. Константы: 0,01 (`0x1001a190`), 0,125, 0,375, 0,5, 0,25. После `__ftol` значение `P` остаётся на вершине стека x87 и используется во всех четырёх ценах — на это спотыкается чтение по Ghidra.
- Маска `0x1001f51c` (надбавки `7 − класс`): всего три обращения (`0x1000b33f` пишет 0, `0x1000b96f` и `0x10005407` читают) — тупик: надбавки не включаются.

- Формат скорости и маневренности на верфи: в `TOWN.dll` есть строка `%.1f` (рядом `%.1f %s`) — одна цифра после запятой; чтение `ships.idf` берёт `speedrate` как float, `turnrate` как целое. Перенесено: `Screen_Decimal` округляет до десятых.

## Магазин (TOWN.dll)

- Склад и цены: `FUN_1000b2e0` (читает `<остров>.gst`); количество: `FUN_1000cdb0`; t: `0x1000848b`.
- Ghidra теряет аргументы `__ftol` (`0x1001225c`) и x87-константы: формулы выведены по дизассемблеру (`objdump -d -M intel`), константы — из PE (`tools/pe_const.py`-способом). `rand` — `0x1001241e`, `rand(n)` даёт 0..n.
- **Множитель цены острова найден.** Начальная цена товара при заполнении магазина (`TOWN.dll 0x1000b779`) = цена из `Goods.idf` × число из записи острова (`+0x276fc`, шаг записи 252 байта) × 0,01, дробь отбрасывается. Число — третье значение `type` острова в `islands_x.idf` (`PdmIslands.<остров>.type`): 130 у Shark Island и Gray Sails, 10 у «мёртвых» вариантов островов (`*_`), у остальных 100. Раньше искали его в записи Highrock, где как раз 100, поэтому казалось, что множителя нет. Перенесено: `Trade_IslandPct`, `Trade_Price0` в `trade.c`, проверка в `Trade_Check`.
- Дата: при открытии магазина `TOWN.dll 0x10008560…0x100085da` берёт дату героя (`+0xf0` день, `+0xf4` месяц, `+0xf8` год), сравнивает с датой последнего визита, хранимой в записи острова (`+0x308/+0x30c/+0x310`; при первом визите пишется текущая), и передаёт в заполнение склада число дней = (месяцы×31 + годы×372 + дни) разницы. Значит, пополнение зависит от прошедших дней, а не от «+15 за визит». Тупик: кто продвигает дату героя, не найдено. Просмотр выгрузок всех DLL из `ref/pdm-decomp` на запись в поля `+0xf0/+0xf4/+0xf8` объекта героя (получается у ядра вызовом `+0xb8` с кодом `0xbc5`) показал, что пишет туда только чужой код с тем же смещением (Cinema, WS_*, SQUAD_CONTROL); в `MAP.dll`, `STATUS.dll`, `TOWN.dll`, `SHIP.dll` дата только читается (`MAP.dll`: дата прибытия = день + дни пути, по модулю 31). В `RESOURCE/QUESTS/*.ql` и `WORLDS/*.idf` полей даты нет. Значит, дату двигает код вне этих DLL (ядро/`ENGINE.exe`), его стоит искать в `ENGINE.exe` или `CORE.dll` по периодическому таймеру. Для ремейка оставлено «+15 дней за визит». Раньше искали, кто продвигает игровую дату героя (`+0xf0/+0xf4/+0xf8`), не найдено — в MAP.dll дата только читается.

### Эскадра в магазине (стрелки PrevShip / NextShip)

Где: `TOWN.dll`, заполнение списка — `0x10008630…0x10008702`, обработчик кнопок магазина `0x1000cfc0` (кнопки 9 и 10, случаи таблицы `0x1000d163` и `0x1000d1c5`); те же кнопки на верфи (`0x1000708e`, `0x100070f1`) листают не флот, а список типов кораблей.
- Список кораблей собирается при открытии: первым идёт сам герой (его корабль), дальше семь слотов спутников героя (`+0x130…+0x148`), в список попадают непустые (с именем). Число — глобальная переменная, индекс выбранного — поле окна.
- «Назад» уменьшает индекс, «Вперёд» увеличивает; на крайнем корабле стрелка гасится (disable); после смены перерисовываются трюм, вес и название корабля.


### Кнопки магазина: какие гаснут при открытии (частично)

Как читать: в объекте окна указатель на узел лежит в конце его записи, `запись + 0x1cc`; записи идут с шагом `0x1d0` в порядке регистрации (`TOWN.dll 0x1000a…`): Exit `0x60`, Sell `0x230`, Buy `0x400`, SCancel `0x5d0`, BCancel `0x7a0`, Left `0x970`, Right `0xb40`, WOnboard `0xd10`, WAllowed `0xee0`, PrevShip `0x10b0`, NextShip `0x1280`, TovarUp `0x1450`, TovarDown `0x1620`, TovarUp1 `0x17f0`, TovarDown1 `0x19c0`, All `0x1b90`, DescUp `0x1d60`, DescDown `0x1f30`.
- При открытии магазина вызовом «+0x10» с нулём гасятся: SCancel, BCancel, All, Left, Right, PrevShip, NextShip (последняя — если корабль один). Кнопки Buy, Sell, Exit остаются.
- Режим сделки — поле окна `+0xf678` (−1: нет). Нажатие Buy/Sell в режиме «нет» не совершает сделку: включает кнопку отмены своей стороны и All, выключает противоположную кнопку (Sell↔Buy) и ставит режим; второе нажатие совершает сделку (деньги, трюм, склад), возвращает режим −1 и снова гасит отмену и All. Отмена (SCancel / BCancel) возвращает всё без сделки.
- Случаи 11–14 таблицы — не Left/Right, а прокрутка списка товаров (клавиши ↑/↓ в окно, только если режим −1). Left/Right (случаи 5, 6) меняют количество; перерисовка `0x1000ccb0` включает их только в сделке.
- В ремейке перенесено: `tradeMode`, `Trade_Arrows` в `trade.c`. Нет: значения режима внутри оригинала (у нас 0/1/2).

### Верфь: фильтр типов (TOWN.dll 0x10004e9f–0x10005100)
При открытии верфи читается `<остров>.sht`; тип попадает в список, если его имя есть в файле и класс в диапазоне [предел−1 .. 6]. Формат: имя файла типа на строку, cp1251.

### Таверна и найм команды: как открываются (тупик)
В диалогах оригинала (`ACTIONS/*.a`, конвертированы в `pdm_logic.c`) `LAUNCH Interface "TOWN"` есть только для `shipyard` и `trade`. Строк `"crew"`/`"tavern"` как имён страниц в `TOWN.dll` нет: в строках только `crewtypes`, `RESOURCE\WORLDS\crew.idf` и узел `ramka_tavern`. Значит, таверна и найм открываются не диалогом — искать вызов в других DLL (не TOWN) либо через меню города. Сценарий для этих экранов пока не сделан.
