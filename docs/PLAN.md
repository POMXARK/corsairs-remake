# Ремастер «Корсаров» на Storm Engine — реалистичный план

Цель: портфолио под GameDev (C++ / Tools / Graphics) и ML (AI Engineering, data/sim).
Принцип: **маленькие законченные этапы**, каждый — отдельный показуемый результат (репозиторий + README + видео/скриншоты «до/после»).

---

## 0. Критика исходного разговора (что верно, что нет)

**Верно и полезно:**
- `storm-devs/storm-engine` — реальный открытый движок (GPL-3.0, открыт в 2021). Это лучшая база: исходники есть, реверс почти не нужен.
- Идея «ML-пайплайн ассетов + C++ движок + симуляция экономики» — сильная связка для резюме.
- Локальная GPU для рутины (апскейл, PBR-карты, mocap, мелкий код) — разумно.

**Ошибки / галлюцинации, которые надо отбросить:**
- «X-Ray / Maelstrom» как сборки Storm — X-Ray это движок S.T.A.L.K.E.R. Что именно открыто, проверять **только по README репозитория storm-devs**, а не по словам чата.
- «Отдельный открытый Storm Engine 2.0 под Корсары 2» — не подтверждено. Открыт один движок; совместимость с ресурсами конкретных игр смотреть в репозитории/issues.
- Universal Modder и REA — проверить самому (существуют ли, лицензия, что реально умеют). Для открытого движка они **почти не нужны**: исходники и так есть.
- «BVH и честный ray tracing в Storm за пару шагов», «перенос на Vulkan интеграцией DXVK в код» — DXVK это транслятор, а не порт. Полный RT — проект на годы, не стартовая задача.
- «Qwen2.5-Coder 32B на 5080» — 16 ГБ VRAM: 32B в Q4 целиком не влезает; реально 14B-класс (или новее, проверить актуальные модели).
- «Claude Code сам делегирует Ollama» — из коробки нет; только через свой MCP-сервер/скрипт или отдельный инструмент (aider/opencode/Continue).
- **Анимации из роликов Black Flag** — нарушение авторских прав Ubisoft и плохое качество. Брать: свои записи с камеры, CMU Mocap, Mixamo (проверить лицензию), открытые датасеты.
- **Цифры в резюме («−70% времени», «−85% затрат», «10 млн транзакций»)** — не писать, пока не измерено. На собеседовании спросят, как мерили.
- Ресурсы игры (модели, текстуры, скрипты) — **не GPL**. Нужна купленная копия (Steam/GOG). В публичный репозиторий кладём только код и свои ассеты, не оригинальные.

**Среда:** рабочий ПК — Windows 11 + RTX 5080 (16 ГБ). Storm Engine собирается под Windows/MSVC — это родная платформа: Visual Studio 2022, RenderDoc, PIX, ComfyUI, Ollama — всё там. Текущая Linux-машина — для заметок/Python-части симуляции.

**Linux-порт:** в репозитории есть `ci_linux.yml` — Debug-сборка на Ubuntu 22.04 (Clang 15, Vulkan, SDL2, Meson, Conan 1.59), тестов нет. То есть порт начат, но полнота (запуск игры целиком) не подтверждена. Доведение Linux-сборки до рабочего запуска ККС — отдельный хороший open-source кейс; делать после Windows-сборки (этап 1), чтобы было с чем сравнивать.

## 1. Этап 1 — Сборка и запуск (1–2 недели)

- [ ] Клонировать `storm-devs/storm-engine`, прочитать README, issues, ветки (статус bgfx, 64-bit, Linux).
- [ ] Определить, с какой игрой совместима текущая сборка (скорее всего ККС/«Каждому своё»), купить её.
- [ ] Собрать Debug + Release, запустить игру.
- [ ] Записать в `notes/engine-map.md` карту модулей: рендер, море, анимация, скрипты, ресурсы (форматы `.gm`, `.tx`, `.ani` и т.д. — сверить с кодом).
- [ ] Настроить RenderDoc-захват кадра (для DX9 может понадобиться запуск через DXVK — проверить).

**Результат для портфолио:** статья/README «Как устроен Storm Engine: архитектура модулей» с диаграммой.

## 2. Этап 2 — Инструменты ассетов (2–3 недели) — Python

- [ ] Конвертеры форматов: текстуры `.tx` ⇄ PNG/DDS, модели `.gm` → glTF (взять логику из кода движка, проверить существующие фанатские тулзы).
- [ ] CLI `storm-tools` с тестами (pytest) на реальных файлах.
- [ ] Импорт glTF → Blender для просмотра.

**Результат:** открытый репозиторий инструментов — сам по себе Tools-Engineer кейс.

## 3. Этап 3 — ML-пайплайн текстур (2–3 недели) — локальная GPU

- [ ] ComfyUI (локально) через API, батч-скрипт на Python.
- [ ] Апскейл (Real-ESRGAN/4x-UltraSharp и т.п.) + ControlNet Tile img2img с низким denoise для деталей.
- [ ] Генерация normal/roughness карт.
- [ ] Обязательно: принудительный resize в степень двойки, сохранение альфы, генерация mip-уровней, сравнение «до/после» автоматически.
- [ ] Метрики качества (хотя бы попарные скриншоты одной сцены + время/текстуру).

**Результат:** пайплайн + видео сравнения. Это ML-часть резюме.

## 4. Этап 4 — Рендер (1–2 месяца) — C++/HLSL

Выбрать **одно** направление, не всё сразу:
- **A (рекомендую):** поддержка normal/roughness карт в шейдерах кораблей/окружения → простой PBR-освещение в существующем рендере. Видимый эффект, контролируемый объём.
- **B:** новая вода (FFT-волны Tessendorf) вместо текущего моря.
- **C:** вклад в переход на bgfx (если ветка жива) — ценно как open-source вклад, но зависит от команды.

Ray tracing / Vulkan-порт — **отложить**. Сначала быстрый эксперимент: игра под DXVK и под RTX Remix — чисто посмотреть, что даёт «бесплатно».

## 4.5 Этап «Редактор» — встроенный редактор на Dear ImGui (параллельно с 4–5)

Полноценного публичного редактора у Storm Engine нет. Цель — не клон Unity, а **in-engine editor** (как debug-инструменты в AAA-студиях):

- [ ] Проверить, есть ли уже ImGui в исходниках (`grep -ri imgui src`); если нет — подключить ImGui (DX9 backend; на Linux — Vulkan/SDL2 backend).
- [ ] MVP: оверлей по F1 — список сущностей/объектов сцены, инспектор параметров (позиция, материалы), FPS/время кадра.
- [ ] Live-tweak: ветер, волны, освещение, время суток — ползунками, с сохранением в ini.
- [ ] Hot-reload текстур и скриптов без перезапуска (сильно ускоряет ML-пайплайн из этапа 3).
- [ ] Гизмо перемещения объектов (ImGuizmo) + сохранение расстановки локации.
- [ ] Браузер ассетов с превью (через storm-tools).
- [ ] AI-слой: команды редактора доступны агенту через `storm-mcp` (агент двигает свет/камеру, делает скриншоты).

Дальше (по желанию, долго): отдельное приложение-редактор, редактор ландшафта/локаций, timeline для катсцен.

## 4.6 Мост в Unreal: плагин-импортёр «Storm → UE5» (после 4.5)

Плагин UE5 (C++), импортирующий ассеты Storm с локальной копии игры: модели `.gm` → Static/Skeletal Mesh, текстуры → материалы, локаторы локаций → расстановка акторов, анимации → Anim Sequence.
- Переиспользует знания формата из `storm-tools` (этап 2).
- Даёт навыки UE5 C++/editor plugins (`UFactory`, Editor Utility, Slate) — самое востребованное в вакансиях Tools/Gameplay.
- Демо: локация ККС (порт) в UE5 с Lumen/Nanite — видео «Storm DX9 vs UE5». Ассеты — только локально (см. «Права на ассеты»).

- [ ] Добавить crossfade/blending между клипами (если его нет или он грубый).
- [ ] Импорт FBX/glTF → формат движка через свой конвертер.

## 6. Этап 6 — Симуляция экономики + ML (1–2 месяца)

Делать **отдельно от рендера**, иначе застрянет:
- [x] Сначала standalone-симулятор на Python: города, товары, торговцы-агенты, пираты, события (блокада, шторм). Правила + RL/эвристики. LLM-агенты — только для небольшого числа «важных» NPC: на сотни агентов в реальном времени это медленно и не нужно.
- [ ] Логирование в Parquet/SQLite, анализ в pandas, прогноз цен (градиентный бустинг/простая сеть), визуализация.
- [x] Потом — мост в движок: экспорт/импорт состояния цен через скриптовую систему игры.

Сделано: `economy/` — модель рынков `trade.c` с агентами, пиратами и штормами, сверка с логами движка, подбор `market.c` через Optuna; отчёт — [ECONOMY.md](ECONOMY.md). LLM-NPC и прогноз цен — впереди.

**Результат:** самостоятельный ML-проект («agent-based market simulation»), который работает и без игры.

### 6.1 Глубина экономики в духе Port Royale (идеи, не ассеты)

Модель мира — то, что делает данные для ML интересными:
- **Производственные цепочки:** сырьё → товар (сахар → ром, хлопок → ткань, древесина → корабли). У города — предприятия с затратами, выработкой, складом.
- **Население и потребление:** каждый класс жителей потребляет корзину товаров; дефицит → рост цен, недовольство, падение роста города; изобилие → рост.
- **Цена = f(запас, потребление, тренд):** не таблица, а реакция на склад; у каждого города свои кривые спроса.
- **Автоконвои игрока и NPC-торговцы:** маршруты, правила «купить ниже X / продать выше Y» — то же, что делают агенты в симуляции.
- **События:** блокада, пиратство, эпидемия, неурожай, война наций → шоки предложения.
- **Строительство игроком:** свои предприятия в городах, лицензии от губернатора.

ML поверх модели:
- [ ] Прогноз цен (бустинг/LSTM) и детекция аномалий (шоки событий).
- [ ] RL-агент торговца против эвристик — метрика: прибыль/день, устойчивость рынка.
- [ ] Балансировка: подбор параметров цепочек (Optuna) так, чтобы экономика не «взрывалась» и не застывала — метрики стабильности цен, Джини богатства городов.
- [ ] LLM — только для слухов/новостей в тавернах по реальным событиям симуляции (текст из данных, не наоборот).

В игру: симулятор крутится «тиками» (день игры), состояние городов отдаётся в скрипты `PROGRAM` через атрибуты; таблицы цен/товаров оригинала — стартовые параметры. Механики Pirates! (дележ добычи, возраст карьеры) — потребители той же модели.

### 6.2 Мультиплеер / кооп (в духе SA-MP) — опционально, после 4–6

В обоих движках сетевого кода нет (проверено grep: winsock/socket/multiplayer — только ложные совпадения). Игра однопользовательская: состояние в атрибутах скриптовой VM, ~450 вызовов `rand()`, пауза в интерфейсах, квесты на одного героя.

Уровни по сложности:
1. [ ] **Морская арена PvP/кооп** — синхронизация кораблей (позиция, курс, паруса, залпы, урон). Авторитарный сервер, ENet или Steam GameNetworkingSockets (`libs/steam_api` уже есть). Реально, хороший C++-артефакт.
2. [ ] **Кооп в море/на карте мира** — хост симулирует, клиент управляет вторым кораблём эскадры.
3. [ ] **Persistent-сервер как SA-MP** — серверные скрипты + экономика из 6/6.1 на сервере (торговый мир на несколько игроков).
4. Полный кооп кампании (квесты, диалоги, сухопутные локации, сохранения) — по сути переписывание игры, не делать.

## Права на ассеты (не юр. консультация)

| Что | Чьё | Можно выкладывать? |
|---|---|---|
| Апскейл/img2img/PBR из оригинальных текстур | производное от оригинала → права у правообладателя игры | нет (только скрипт обработки) |
| Сгенерировано с нуля (txt2img, text-to-3D) | человеческого авторства нет → защиты может не быть; условия — по лицензии модели/сервиса | да, если лицензия модели/сервиса позволяет |
| Сделано руками (в т.ч. на базе ИИ-заготовки, с существенной доработкой) | твоё в части доработки | да |
| Код движка | GPL-3.0 → твои изменения тоже GPL | да, с исходниками |

Проверять лицензии: веса модели (у части моделей запрет коммерции), бесплатные тарифы 3D-сервисов (выход может быть публичным / CC BY), mocap-датасеты.

**Схема распространения «bring your own assets»:** публикуем только код + пайплайн; пользователь запускает его на своей купленной копии игры, ассеты генерируются локально. В портфолио — видео/скриншоты «до/после».

## Отладка (сквозные правила)

- Логгер загрузки ассетов: путь, размер, формат, число костей → видно, на чём падает.
- Валидация ассетов **до** игры в `storm-tools` (размер степени двойки, число костей, формат).
- Каждое изменение — за фича-флагом в конфиге: старый/новый рендер переключаются без пересборки.
- Эталонные сцены + скриншоты для визуальной регрессии.

## AI-native слой: «разработчик нового времени»

Цель — показать не «пользуюсь ИИ», а **умею строить и измерять AI-инфраструктуру разработки**. Это делается параллельно с этапами 1–6 и даёт отдельные артефакты.

### 7.1 Свой MCP-сервер `storm-mcp` (главный артефакт)
Python, открытый репозиторий. Инструменты для агента:
- `build(config)` — сборка движка, возврат ошибок компилятора в структурированном виде;
- `run_scene(name)` + `screenshot()` — запуск эталонной сцены, скриншот;
- `read_log(filter)` — логи движка/ассетов;
- `inspect_asset(path)` — разбор `.gm`/`.tx` через `storm-tools` (этап 2);
- `validate_assets(dir)` — проверка степеней двойки, костей, форматов.

Итог: агент (Claude Code) сам цикл «правка → сборка → запуск → скриншот → проверка». Это и есть agentic workflow, который можно показать на видео.

### 7.2 Гибрид облако + локальная GPU
- Ollama/llama.cpp на 5080, модель ~14B-класса для кода.
- Маршрутизация: рутина (комментарии, шаблонные правки, суммаризация логов) → локально; архитектура/сложный C++ → Claude.
- Реализовать как инструмент в `storm-mcp` (`local_llm(task)`), а не «вручную копировать».

### 7.3 Evals — то, что отличает инженера от пользователя
- Набор из 20–30 реальных задач по движку (исправить ошибку сборки, написать конвертер, найти функцию загрузки).
- Прогон: Claude vs локальная модель vs вручную. Метрики: доля успешных, время, стоимость, число итераций.
- Таблица результатов в README. **Именно эти цифры** потом идут в резюме — честные и проверяемые.

### 7.4 Контекст и память агента
- `CLAUDE.md` в репо движка: архитектура, правила сборки, запреты (не трогать оригинальные ассеты и т.д.).
- `notes/` — field notes, которые агент дополняет: что ломалось и почему.
- Пример промптов/сессий в репо — показывает, как ты ставишь задачи.

### 7.5 Инженерная гигиена (без неё AI-код не воспринимают всерьёз)
- CI (GitHub Actions на Windows): сборка + pytest для `storm-tools` + валидация ассетов.
- Визуальная регрессия по эталонным сценам.
- Каждый PR агента проходит твоё ревью; в описании PR — что проверено.
