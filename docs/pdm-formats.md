# Форматы оригинальных «Корсаров» (PDM 1.061) и их конвертация

Что проверено на файлах игры и чем конвертируется в форматы Storm 2. Справка по форматам — [AlexKimov/seadogs-file-formats](https://github.com/AlexKimov/seadogs-file-formats) (шаблоны 010 Editor, плагины Noesis, wiki); ниже то, где она неполна или ошибается.

## Конвертер всего RESOURCE

```
tools/convert.sh  <папка_игры> <out>     # Linux / macOS
tools\convert.bat <папка_игры> <out>     # Windows (вызывает convert.ps1)
.\tools\convert.ps1 <папка_игры> <out>   # PowerShell
```

Все три — обёртки над `tools/pdm2storm.py` (нужен только Python 3.8+, для моделей — submodule `engine`). Ключи: `--only textures,models,...` — выбрать этапы, `-j N` — число процессов. На 16 ядрах весь PDM конвертируется за ~40 секунд:

| этап | что | куда | PDM 1.061 |
|---|---|---|---|
| textures | `.tf` → `.tx`, `.tga` без `.tf`-двойника → `.tx` | `out/resource` | 3167, 0 ошибок |
| models | `.cff` → `.gm` | `out/resource` | 677, 3 битых в оригинале |
| copy | остальное как есть (звук, ini, тексты, `.ani`…) | `out/resource` | 3232 |
| actions | `.a` → команды | `out/data/actions` | 715 |
| dialogs | `.d` → узлы, ссылки, действия | `out/data/dialogs` | 1108 |
| tables | `.idf` → объекты name/value | `out/data/tables` | 96 |
| desc | `.def` → локаторы частей корабля | `out/data/desc` | 97 |
| characters | `.mtx` → карточки персонажей | `out/data/characters` | 297 |
| ships | `.shp` → профили кораблей | `out/data/ships` | 94 (+1 шаблон старой версии) |
| quests | `.ql` → сюжетные линии: квест, условие, действие | `out/data/quests` | 76 |

`out/resource` читает движок, `out/data` — JSON в UTF-8 для игровых скриптов. Итог с ошибками — в `out/convert-report.json`. Папку для запуска движка собирает `tools/make_korsari_run.sh <PDM> <sd-teho-public> <out> [engine/build/Debug]` (тот же конвертер + ini и скрипты TEHO + шейдеры).

## TF — текстуры → `.tx` (`tools/tf2tx.py`)

```
0x05  u8   pixel type
0x06  u8   число 16-битных мипов
0x07  u8   число 8-битных палитровых картинок
0x08  u32  width, u32 height
0x10  мипы 16 bit, затем палитра 256×4 (R,G,B,pad), затем 8-битные индексы
```

| type | формат | файлов в PDM |
|---|---|---|
| 0 | R5G6B5 | 2338 |
| 1 | A1R5G5B5 | 388 |
| 2 | A4R4G4B4 | 16 (такелаж, Blob, курсоры) |

- `TF.bt` путает типы 0 и 1. Проверка: у type 1 в раскладке A1R5G5B5 соседние пиксели отличаются в среднем на 3.4 на канал, в R5G5B5A1 — на 12.3, то есть получается шум.
- **Альфа инвертирована**: установленный бит (у type 2 — 15) означает прозрачность. Проверено на `Dama_Body` (прозрачен только зигзаг сверху) и `mf_takelag` (прозрачны промежутки между верёвками).
- Палитровые картинки — запасной вариант, если 16-битных мипов нет.

## TGA — картинки интерфейса → `.tx` (`pdm2storm.py`)

425 из 450 TGA не имеют `.tf`-пары: иконки товаров, кнопки, фоны, карта. Все несжатые (image type 2):

- 305 файлов — 16 бит A1R5G5B5. Альфа-бит, как и в `.tf`, означает прозрачность: он не стоит ни в одном файле, и всё это непрозрачные картинки интерфейса. По стандарту TGA они вышли бы полностью прозрачными.
- 105 — 32 бит без альфы, 40 — 32 бит с обычной 8-битной альфой (гербы, свиток, такелаж, шрифты).
- Строки снизу вверх, если не стоит бит 0x20 дескриптора; `.tx` хранит сверху вниз.
- Надписи на карте (`MermaidReefs`, `goldway`…) имеют альфу 0 во всех пикселях: видимо, игра рисовала их аддитивно. Конвертер переносит альфу как есть.

## CFF — модели → `.gm` (`tools/cff2gm.py`)

Заголовок, текстуры, материалы и меши — как в [cff-format/README.md](cff-format/README.md). Чего там нет:

- **Вершина 13 или 12 байт.** 653 файла используют 13 байт (i16×3 pos, i16×2 uv, u8×3 color). 26 старых файлов (`torus`, `Shlop`, `tavern_new`, `Panorama`, …) — 12 байт: заголовок следующего меша начинается ровно после `vc*12 + fc*3`.
- **Кадр анимации 0 ставит часть на место.** У мешей персонажей и катсцен (`*_a.cff`) вершины лежат в локальной системе части. 28-байтный ключ: translation 3f, rotation 3f (радианы), номер кадра u32. Позиция: `v' = Ry·Rx·Rz·v + t`, как в `D3DXMatrixRotationYawPitchRoll`. Порядок выбран перебором на 84 персонажах по зазору в суставах: этот вариант выиграл в 65 случаях, следующий — в 8. В плагине Noesis ось Y повёрнута в другую сторону.
- Расширения в разном регистре (`.cff`, `.CfF`, `.Cff`) — искать без учёта регистра.
- Битые в оригинале: `ABrigCan.cff` (меш 59 на 2 байта короче заголовка) и `Reef.CfF` (`MaterialCount = 0xCCCCCCCC`, неинициализированная память MSVC). Игра, видимо, их не грузит. Конвертируется 677 из 679.

## A — скрипты действий (`tools/a_decode.py`)

Каждый байт `i` в 8-байтном блоке циклически сдвинут вправо на `i` бит. Алгоритм — `scripts/010editor/decodeActionFile.1sc`. После декодирования получается текст cp1251 на простом DSL, одна команда в строке:

```
SET_FOR Person "X" Location "Shark Island.tavern"
ADD Item "..." "1"
LAUNCH Story_line "Spanish_line"
```

### Как CORE.dll читает команду

Интерпретатор (`CORE.dll`, функция `0x100014a0`) берёт первое слово строки до пробела, табуляции или перевода строки и сравнивает его без учёта регистра с таблицей команд. Затем читает пары `<Тип> "значение"`; у `Item` и `Goods` есть второе значение в кавычках — количество.

Команды (индекс = номер в таблице): `CLOSE, ADD, DELETE, SET_FOR, COMPLETE, DESTROY, PLAY, LAUNCH, CHECK, ADVANCE, OPEN, MESSAGE BOX, SET`.

Типы объектов (у каждого в таблице есть сигнатура аргумента: `s` — строка, `l` — число, `sl` — строка и число):
`Person, Game, Ship, Item, Goods, Record, Quest, Location, Expirience, Module, Characteristics, File, Rank, Dialog, DLink, Story_line, String, Interface, Playside, Model, Reputation, DNode, State, Officer, Officer_Rank, Engine_movie, Quantity, hull_hp, team_hp`.

Что делают ветки, которые встречаются в данных:

| Команда | Что делает | Строк |
|---|---|---|
| `SET State "0" DLink "диалог:узел:ссылка"` | включает или выключает ссылку диалога | 522 |
| `SET_FOR Person "X" Dialog "Y"` | назначает персонажу диалог `DIALOGS/Y.d` | 398 |
| `SET_FOR Person "X" Location "остров.локация"` | телепорт; `void` убирает персонажа | 320 |
| `SET_FOR Story_line "L" Quest "Q"` | переключает линию на квест и запускает его действие | 224 |
| `ADD Record "R"` | запись в журнал `TEXTS/RECORDS/R.rcd` | 204 |
| `ADD`/`DELETE Item "money" "N"` | деньги; иначе — предмет | 214 |
| `ADD Expirience "N"` | опыт | 110 |
| `ADD`/`DELETE Reputation "N"` | репутация | 97 |
| `LAUNCH Story_line "L"` | открывает сюжетную линию | 74 |
| `OPEN Location "остров.локация"` | переносит игрока в локацию | 50 |
| `ADD`/`DELETE Person "X"` | персонаж в эскадру игрока или из неё | 55 |
| `SET_FOR Person/Location … Playside "нация"` | меняет нацию по `nations.idf` | 46 |
| `PLAY Engine_movie "M"` | ролик | 28 |
| `SET_FOR Person "X" Model "M"` | модель `characters/M.cff` | 24 |
| `ADD`/`DELETE Officer`, `Goods`, `SET_FOR Person … Ship/Item` | офицеры, груз, корабль `SHIPS/*.shp`, передача предмета | ≤ 20 каждая |
| `CLOSE Game "X"` | конец игры | 5 |

Сюжетную линию двигают сообщения в `CORE`: 9001 переводит линию на следующий квест и выполняет его действие, 9002 ставит квест по имени. После этого `CORE` до 5000 раз повторяет проверку, пока переходы идут каскадом.

**Мёртвый код в данных.** Таблицу команд ищут по одному слову, поэтому `MESSAGE BOX …` (16 строк, всплывающие подсказки) не совпадает ни с чем. `message_box` и `END` (2 строки) в таблице тоже нет. Все они игнорируются: эти подсказки в оригинале никогда не показывались. `test_dima.a` не расшифровывается ни одним сдвигом — тестовый мусор.

Конвертер раскладывает каждую строку по этим таблицам. В JSON у команды есть поля:

- `cmd` — каноническое имя команды; `null`, если `CORE` её проигнорирует, тогда рядом стоит `note`;
- `objects` — список `type` / `value` / `count`;
- `effect` — что делает команда.

## D — диалоги

Обычный текст cp1251: `<N узел>`, `<T реплика>`, `<L ссылка,вкл,?,узел>` и следом `<T ответ героя>`. Файл `DIALOGS/<id персонажа>_<диалог>.d`: `salvadore engano_common.d` — диалог `common` трактирщика Salvadore Engano. Узел `exit` закрывает разговор. Второй флаг ссылки почти всегда равен первому, его смысл не найден.

Как диалог доходит до игры:
- в карточке `.mtx` поле `dialog = common.dlg` — начальный диалог. Генератор переводит его в `Pdm_SetDialog(<персонаж>, <id>_common)` в `PdmLogic_Init` (634 персонажа, у 56 поле пустое). Дальше диалог меняют действия `SET_FOR Person … Dialog`;
- разговор начинается с первого узла файла: `PdmDialogs.<диалог>.start`;
- окно рисует `DIALOG_TERMINAL.dll`. В `INI/fonts.ini` секция `[DialogTerminal]`: шрифт `23,5,log-russ-Italic`, речь NPC цветом `rgb_npc_speech = 225,240,191`, ответы — `rgb_our_speech = 255,255,255`, с тенью. Картинки окна нет (`TEXTURES/dialog` пуст);
- голос: `SOUNDS/<id персонажа>.wav` (PCM 22 кГц моно, 252 персонажа) — фраза при начале разговора.

`pdm_ui.py` переводит `[DialogTerminal]` в `ini/dialog.ini` сущности `dialog`. Шрифт берётся тот же свободный, что у меню, с размером и цветами оригинала; окно — из `engine/demos/dialog/make_dialog.py`. Голоса копируются в `sounds/voices/<ключ>.wav`, а `program/data/pdm_voices.c` пишет их в `PdmCharacters.<ключ>.greeting`.

`program/town.c` ведёт разговор:
- клавиша E — ближайший NPC в радиусе 3 м, у которого есть `dialog_key`;
- узел: `Dialog.Text` — реплика, `Dialog.Links.<ссылка>` — включённые ссылки (`on = 1`);
- выбор вызывает `Pdm_DialogChoose`: выполняется действие ссылки, проверяются квесты, разговор идёт в узел `to` или закрывается на `exit`.

Проверка без нажатий: `SCENE=town TOWN_AUTO=2 pdm-game/run.sh build/Debug/engine`. Герой заходит в таверну, подходит к первому NPC с диалогом (падре Игнасио) и проходит дерево `padre_ignacio_first`, каждый раз выбирая первую включённую ссылку. Ответ «И у меня найдется койка для вас, падре» выполняет действие ссылки, и падре получает диалог `padre_ignacio_agreed`.

## IDF — таблицы (`pdm2storm.py`, этап tables)

`u32, u32 count, u32`, затем `count` объектов: `u32 n` + `n × 132` байт (`u32` мусор/указатель, `name[64]`, `value[64]`, cp1251). Разбираются все 96 файлов до последнего байта. Порядок объектов важен: другие файлы ссылаются на них по индексу (`nation` в `.mtx` — номер в `nations.idf`: 0 england, 1 pirate, 2 france, 3 spain; груз `.shp` — номера в `Goods.idf`).

## DEF — устройство корабля (этап desc)

`u32 count` + `count × 296`: `u32 index, u32 class, u32 sub, char file[256], float pos[3], float rot[3], i32 link` ([DEF.bt](https://github.com/AlexKimov/seadogs-file-formats)). Классы 200–209: Model, Rey, Sail, Cannon, Flag, Waterline, Patch, CannonSet, AllCannons, ShipTrace; 210–212 встречаются, смысл не известен.

Сборка корабля — `tools/pdm_ship.py <PDM> <resource> <Ship>`. Скрипт берёт из DEF элементы `Model`: корпус, мачты `_ms*`, такелаж `_Tklg`, пушки `_can`. `Patch` (`ABrig_Patch.cff`, текстура `black`, все грани смотрят вниз) — чёрная крышка над трюмом, видимо маска, не пускавшая море оригинала внутрь корпуса; Storm 2 она не нужна. Обмотка граней в CFF не согласована: зеркальные половины (левая половина носа брига) записаны с обмоткой оригинала и смотрят внутрь — движок PDM рисовал без отсечения. Поэтому `cff2gm` делает грани двусторонними: к каждой добавляется обратная копия с противоположной нормалью. Смещение каждой части — сумма `pos` по цепочке `link`; модели частей не повёрнуты. Все части пишутся в один `models/ships/<Ship>/<Ship>.gm` в метрах (×26: ABrig длиной 1,17 единицы становится бригом около 30 м), их текстуры — в `textures/ships/<ship>/`. Флаги пока не переносятся.

Такелаж в Storm 2 рисуют сущности, а не модель, поэтому части CFF с ним становятся метками `.gm`:

- **Штаги** — тонкие треугольники `ABrig_Tklg.cff` (текстура `black`): у каждого короткая сторона — один конец троса, противоположная вершина — другой. Из них получаются метки `ropeb<N>` / `ropee<N>` для сущности `rope`, круглого троса, видного с любой стороны.
- **Ванты** — одиночные треугольники `takelag_new` в CFF мачт: вершина у топа мачты, два угла у борта. Из них получаются метки `vant<N>u/l/r` для сущности `vant`. Номер в имени метки — одна цифра, поэтому 10-я и следующие ванты идут как `vanx<N>` для сущности `vantl`.

Текстуру `black.tf` для тросов брать нельзя: её альфа падает с каждым мип-уровнем (255, 187, 136, 85, 34). Так оригинал гасил тонкий такелаж на расстоянии, а техники `ShipRope`/`ShipVant` с альфа-тестом выбрасывают такой трос уже в нескольких десятках метров. Поэтому `pdm_ship.py` генерирует свои `sail_rope.tga` и `vant.tga`. Их мипы берут максимум альфы по блоку 2×2, и тонкие линии видны издали. Раскладка `vant.tga` и толщина тросов пишутся в `ini/rigging_pdm.ini`, а `run.sh` дописывает их в `rigging.ini`. Ещё одна ловушка — `fMaxDist` в `[ROPES]`: движок сравнивает с ним квадрат расстояния до корабля, умноженный на tg(fov/2). Значение по умолчанию 5000 прячет тросы дальше ~90 м, и при облёте они мигают.

## DEF острова (`tools/pdm_island.py`)

Остров устроен как корабль: `DESC/<Остров>.def` с элементами `Model` (суша `<Остров>.CFF`, форты вроде `HighrockFORT.cff`), `Cannon` (пушки форта) и `Flag`. Масштаб тот же, ×26: Хайрок — около 1430 × 1030 м и 315 м в высоту. Имя `.def` — поле `name` из `WORLDS/islands_x.idf` без `_` (запись с `_` — мёртвый город на том же острове); имя модели Storm — только буквы и цифры (`Gray Sails` → `GraySails`).

- Меш с текстурой `wsea*` — полоса мелководья у города, которую оригинал рисовал поверх своего моря. В модель он не идёт (у Storm своё море), его центр считается гаванью.
- Суша и форты пишутся в `models/islands/<Остров>/<Остров>.gm` с BSP (по нему `touch` и камера находят берег), текстуры — в `textures/islands/<остров>/`.
- Карта глубин `foam/islands/<Остров>.tga` + `.ini`: 8-битная 512 × 512 по боксу модели + 50 м; пиксель 2 — суша, `2 + 253·глубина/20` под водой. Без неё движок при первой загрузке трассирует 2048² лучей (минуты в Debug); кэш `.tga.zap` конвертер удаляет.
- Место корабля — ближайшая к гавани точка не ближе 120 м от воды мельче 6 м, нос к гавани; оно и сама гавань (`harbour_x/z`, по ней корабль заходит в порт) пишутся в `data/islands/<Остров>.json`, `pdm_data2c.py` кладёт его в `PdmIslands`. Там же `exit_r` — расстояние от гавани до дальнего угла бокса острова + 600 м: дальше корабль уходит на карту мира.

## Карта мира (`MAP.dll`, `INI/map.ini`, `map.c`)

- Пергамент `IMAGES/MAP/RUSSIAN/map_open.tga` 1200 × 900 с нарисованными островами (`map_close.tga` — неоткрытый). Виден в окне `map_pos 31,27`, `map_rect 0,0,587,484` секции `[MainMap]`; окно следует за кораблём.
- `map_cell = "клетка,x,y"` записи острова в `islands_x.idf`: сетка 20 × 15 по 60 px, x, y — где рисуется флаг, около 35 px над островом.
- Корабль — `IMAGES/MAP/ship.tga` 35 × 24, нос вправо, чёрный — прозрачный; при курсе на запад отражается.
- В список идут острова с моделью у моря (`port_x`) и `map_cell`, без мёртвых городов `_`, под русским именем из `TEXTS/RUSSIAN/GOODS/ISLANDS/<Остров>.nme` (cp1251, одна строка; `pdm_island.py` пишет его в `label`).
- Клик по пергаменту выбирает остров, чей `map_cell` (+35 px) ближе 60 px к курсору (наше: `MAP.dll` так не умел).
- Экран 4:3. На окне шире или уже `map.c` режет фон и повторяет полосу из его середины (`BACK_TILE<n>` от `pdm_ui.py`): рамка удлиняется без растяжения, окно карты показывает больше пергамента, панель со списком прижимается к правому верхнему углу.

## SLS — паруса (`DESC/<корабль>.sls`, `pdm_ship.py`)

Записи идут подряд до конца файла, по одной на элемент DEF класса `Sail`:

```
u32 item            индекс элемента DEF
u32 0
f32 belly           глубина пуза паруса (отрицательная)
f32 corners[4][3]   углы паруса от позиции элемента: верх-лево, верх-право, низ-право, низ-лево
u32 meshes          реи этого паруса
  char texture[32]  af_reya.tga
  u32 nv, nt
  nv × { f32 pos[3], f32 normal[3], u32 colour }
  nt × { u16 a, b, c, pad, f32 uv[3][2] }   UV у каждого угла треугольника, а не у вершины
```

`ABrig.sls` (5216 байт) — 9 парусов на трёх мачтах. Подтип DEF `sub 4` — гафельный парус бизани, остальные прямые. Реи идут в модель мешами `yard<item>`. Полотно рисует сущность `sail` по четырём меткам углов `sail1..4` в группе `sails<item>` (прямой парус, сворачивается) или `sailf<item>` (трапеция, гафель). Ткань — `parus_all.tf`, а `parus1..3` — та же ткань, порванная.

## MTX — персонажи (этап characters)

2384 байта (`0x950`). `CHARACTER_EDITOR.dll` (`FUN_10003dc0`) собирает их поле за полем из объекта редактора, обратная функция — `FUN_10003ef0`. Первый `u32` — размер, по нему файл и проверяется.

| смещение | поле | подпись в редакторе |
|---|---|---|
| 0x058 | `char[32]` имя (рус.) | name |
| 0x078 | `char[32]` id, он же имя файла | file name |
| 0x0a8 | `i32` нация, индекс в `nations.idf` | nation |
| 0x0ac | `i32` отношение, индекс в `relations.idf` | relation |
| 0x2b4 | `i32` тип: 0 — обычный NPC, 2 — капитан с кораблём, 1 — три квестовых NPC | character is |
| 0x2c8 | `char[32]` модель `CHARACTERS\*.cff` | 3D model |
| 0x2e8 | `char[32]` корабль `*.shp` | ship |
| 0x308 | `char[64]` текущий диалог | current dialog |
| 0x348 | `char[64]` остров, 0x388 `i32` — номер локации | address («A:%d on island: %s») |
| 0x734 | `i32[9]` навыки: Sailing, Repair, Commerce, Accuracy, Reload, Coordination, Combat, Defence, Board Range | |
| 0x934 | `i32` ранг офицера: −1 нет, 0 FIRST_MATE … 5 CARPENTER | officer rank |

Порядок навыков подтверждается данными: у казначея Адама Муллена (ранг 2, MASTER_PURSER) ненулевой только третий навык — Commerce. Остальные непустые слова конвертер кладёт в `unknown`. У 96 персонажей в 0x0b0 лежит `0xCCCCCCCC` — неинициализированное поле.

## SHP — профили кораблей (этап ships)

792 байта: `u32` + структура `0x2f0` + блок `0x24`. Их пишет `TOOLS_SHIPEDITOR.dll` (`FUN_10004ad0`, три `fwrite`), а читает `FUN_10004c40`. Поля сопоставлены с формой редактора:

| смещение | поле |
|---|---|
| 0x000 | Player skill (1–12) |
| 0x008 | `char[32]` имя профиля |
| 0x028 | `char[32]` класс корабля из `Ships.idf` (Ship type) |
| 0x04c | Hull HP (0x048 обычно то же число — вероятно, Rig HP) |
| 0x05c | Crew number |
| 0x084 | Weapon type: 0 Demi-culverins, 1 Culverins, 2 Demi-cannons |
| 0x090 | `i32[128]` груз: количество по индексам `Goods.idf` (пушки, ядра, книппели, картечь, бомбы, товары) |

## QL — сюжетные линии (этап quests)

Файл `.ql` — одна сюжетная линия (story line), записи в нём — её квесты. Пишет их `QUEST_EDITOR.dll` (`FUN_10004570` дописывает квест в конец и обновляет счётчик в заголовке). Разбираются все 76 файлов до байта.

```
u32 0, u32 count, u32 0
count × {
  u32 0, u32 data_len, u32 указатель кучи (мусор)
  char name[64]        имя квеста; "void" — пустое состояние линии
  char action_alt[64]  действие (3 случая)
  char action[64]      ACTIONS/<action>.a, выполняется, когда условие выполнено (106 из 106 есть в ACTIONS)
  char extra[64]       всегда пусто
  u8 data[data_len]    условие
}
```

Условие: `u8 condition, u8 object`, дальше по типу — `u32 len + строка`, `i32` значение или и то и другое. Для ESCORT добавляется цель: `u8 object (7 = Location), u32 72, name[64], i32, i32`. Имена взяты из таблиц указателей в `.data` DLL, а не из выгрузки строк: короткое `KILL` в неё не попало.

| condition | object | пример |
|---|---|---|
| 0 NO CONDITION | — | `void` |
| 1 OBTAIN | 3 Item, 4 Goods + количество | `Item "money" 5000`, `Goods "Chocolate" 150` |
| 1 OBTAIN | 12 Rank, 20 Reputation | `Reputation 5` |
| 2 KILL | 0 Person | `Person "Frederick The Mole"` |
| 3 ESCORT | 0 Person → 7 Location | `"Tedoro Alameda"` → `sinistra` |
| 4 MATCH | | в PDM не встречается |

Типы объектов (индекс): Person, Game, Ship, Item, Goods, Record, Quest, Location, Expirience, Module, Characteristics, File, Rank, Dialog, DLink, Story line, String, Interface, Playside, Model, Reputation, DNode, State, Officer, Officer Rank, Engine movie.

Как это связано: действие `.a` запускает линию (`LAUNCH Story_line "X"`) или переключает её квест (`SET_FOR Story_line "Mullen_check_1000" Quest "void"`). Движок проверяет условие текущего квеста, а когда оно выполнено, запускает его `action`. Тот, в свою очередь, двигает линию дальше, выдаёт предметы, меняет диалоги персонажей (`SET_FOR Person "X" Dialog "Y"`).

## Конвертер логики (`tools/pdm_logic2c.py`)

`run.sh` переводит всю сюжетную логику в `program/data/pdm_logic.c`, а исполняет её `program/story.c`. Сводка: 715 действий (2461 команда), 76 линий, 554 диалога (2887 ссылок), 12 пропусков. Все пропуски — битые ссылки самого оригинала: нет `Quest_1`/`Quest_6`.ql, персонажей Friend и Stranger with an accent, узлов Roberto Gorrando `No_yet`/`Ready_to_action`, квеста `French_line:Capture_Ballena`, предметов Brin's letter и `money2000`.

Шаблон:
- каждое `.a` превращается в функцию `PdmA_<имя>()`; каждая из 30 видов команд — это вызов одного из 24 примитивов (`Pdm_SetQuest`, `Pdm_SetDLink`, `Pdm_AddItem`, `Pdm_SetDialog`, `Pdm_OpenLocation` …);
- линия хранится в `PdmLines.<линия>`: `launched`, `current` и квесты `q<i>` с полями `action`, `enter`, `cond`, `kind`, `target`, `value`, `to`;
- диалог хранится в `PdmDialogs.<диалог>.<узел>.<ссылка>`: `text`, `to`, `on`, `action`; `Pdm_DialogChoose` выполняет действие включённой ссылки;
- `story_lines.idf` задаёт линии, открытые в новой игре (`PdmLogic_NewGame`).

Семантика `CORE.dll`:
- `action_alt` выполняется при входе в квест (`SET_FOR Story_line … Quest …`): так в новой игре выдаётся медальон;
- когда условие выполнено, выполняется `action`; если действие не сдвинуло линию, она переходит к следующему квесту (сообщение 9001), а после последнего закрывается; каскад ограничен 5000 шагами;
- `SET_FOR Person … Item N` задаёт количество, а не прибавляет: в данных встречаются зарплаты -700 и 0;
- имена сравниваются без учёта регистра, `_` равно пробелу (`add_medallion` = `add medallion`);
- копия `RESOURCE/INI/DIALOGS` не используется, только `RESOURCE/DIALOGS`.

Проверка: `SCENE=story pdm-game/run.sh build/Debug/engine` — новая игра, цепочка каперского свидетельства Англии и запуск всех 715 действий; в `compile.log` строки `PDM story test: ok …`.

## Интерфейс (`tools/pdm_ui.py`)

Все экраны оригинала (`INI/menu.ini`, `town.ini`, `status.ini`, `ransack.ini`, `map.ini`) описаны одной грамматикой. Их читают `MENU.dll`, `TOWN.dll`, `STATUS.dll` и другие модули. Экран — секция INI на виртуальном экране 800×600:

| ключ | пример | что это |
|---|---|---|
| `background` | `..\fons\menu-fon-$.tga` | картинка под экраном, `$` — язык |
| `ramka` | `1,100,48,700,552` | рамка из кусков `frames\<тип>.tga` |
| `titleN` | `txt:"#MenuTitle#",font:"seadogs,56,0",xo:400,yo:103,rgb:"255,230,115"` | надпись |
| `lb_<Имя>` | `txt:"#MenuNewGame#",file:"..\buttons\mbutton",xo:400,yo:160,font:…,rgbn/rgba/rgbd/rgbi:"r,g,b"` | кнопка: картинки `<file>-{nor,hi,down,dis}.tga`, цвет текста в обычном, выбранном, нажатом и недоступном состоянии |
| `t_<Имя>` | `#YouWant2Exit#` | текст окна-вопроса |

Правила разбора:
- **Координаты:** `xo`/`yo` — центр, `xl`/`yl` — левый/верхний край, `xr` — правый край.
- **Причуда данных:** вместо запятой бывает двоеточие (`xr:585:yo:175` в `[Options]`).
- **Пути:** отсчитываются от `[Common] path = MENU\` и не зависят от регистра: на диске `IMAGES/FONS`, `BUTTONS`.
- **Шрифт:** `"logbook,27,0"` — имя из `INI/fonts.ini` и высота строки, как её принимает `CreateFont`. В `[russian]` у имени гарнитура и масштаб: `logbook = 0.97,…,log-russ`, `seadogs` → `seawolf`, `desc` → `Interface`. Самих TTF в папке игры нет: установщик кладёт `seadogs10..13.ttf` (Log-Russ, Log-Russ-Italic, SeaWolf_L, InterFace) в `Windows\Fonts`, а деинсталлятор их удаляет.
- **Прозрачность:** у картинок нет альфы, прозрачный цвет — чёрный (углы кнопок, фон курсора `cursor.tga`).

Конвертер выдаёт экраны XINTERFACE:
- `background` → `PICTURE` (текстура 1024×1024, `textureRect 0,0,1,0.75`);
- `titleN` → строка `STRINGCOLLECTION`;
- `lb_*` → `TEXTBUTTON`:
  - кнопки `nor`/`hi` складываются в атлас, их половины — левая и правая части кнопки, середина шириной 2 px;
  - цвета `rgbn/rgba/rgbd/rgbi` → `fontColor/fontColorSelected/fontColorPressed/unselectableFontColor`;
  - соседние кнопки связаны `upstep`/`downstep`;
- тексты `TEXTS/RUSSIAN/INI/interface.ini` (616 строк) → `ini/texts/russian/common.ini`, ключ `#Key#` → `string = Key`;
- каждая пара шрифт+размер → свой шрифт движка `pdm_<имя>_<размер>`:
  - гарнитура ищется по имени семейства (`ImageFont.getname`) в папках: `PDM_FONTS`, папка игры, `~/.local/share/fonts`, `~/.fonts`, `/usr/share/fonts`, `/usr/local/share/fonts`, `drive_c/windows/Fonts` префиксов Wine (`~/.wine`, `~/Games/*`, `~/.local/share/wineprefixes/*`), `%WINDIR%\Fonts` и шрифты пользователя Windows;
  - без оригинала подставляются свободные: `log-russ` → PT Serif Regular, `Interface` → тоже PT Serif Regular (жирный в 14 px расплывается на пергаменте), `seawolf` → Old Standard Bold (OFL). Old Standard с обводкой в мелких кеглях не читался, поэтому текст набран PT Serif;
  - оригинал печатает через GDI без обводки и тени: глифы рисуются без обводки (кроме заголовков seadogs от 30 px), а у каждого шрифта в `fonts.ini` стоит `No_shadow` — иначе узлы XINTERFACE кладут тёмную копию в 2 px и текст двоится;
  - рисуется в 1,5 раза крупнее и уменьшается узлом — в окне больше 800×600 текст остаётся чётким;
  - `interface_normal` нужен редактору XINTERFACE всегда;
- курсор → `MousePointer`.

`[PC_SCREEN] bDynamicScaling = 1` ставит экран 4:3 по центру широкого окна. Без секции `[PC_SCREEN]` прямоугольник экрана получается перевёрнутым (`wScreenTop` по умолчанию 600, `wScreenDown` — 0), и ничего не рисуется.

Остальные экраны (`town.ini`, `status.ini`, `ransack.ini`, страницы `menu.ini`) добавляют к грамматике:
- `[Common]` с полями `EditDesc`, `EditFaceName`, `EditFaceMoney`, `EditTitle`… — они есть на каждом экране файла, если экран не задаёт их сам;
- `Edit<Имя>` — поле, которое заполняет DLL (имя, деньги, корабль) → `FORMATEDTEXT`, его заполняет `program/screens.c`;
- `s_<Имя> = txt:"Ранг %d"…` — шаблон значения статуса → `FORMATEDTEXT`; шаблоны строк списков (`yo` меньше 40 — смещение строки) остаются комментариями;
- `@rgb_small@` — макрос цвета из `[Common]`;
- `lb_*` без `file` — кнопка-надпись → `FORMATEDTEXT` с откликом на клик;
- `title*` с `file:..\frames\m_titles.tga` — табличка под надписью → `PICTURE`;
- рамки, виньетки и прокрутки рисует C++ модулей — в экране они остаются комментариями `; ключ = значение`;
- строки списков тоже рисует C++, но `p_ShipTovarName = 80`, `p_ShipOnboard = 219`… дают x колонок в `EditShipTovars`/`EditShopTovars`. Каждая колонка → `FORMATEDTEXT LIST_<КОЛОНКА>` во всю высоту списка, одна строка — одна строка таблицы (`\n`). Название прижато влево до следующей колонки, числа — по центру в 80 px (наше). Колонки, которые не лежат в одной рамке `ramka_*` (`[SChest]`), — не таблица: сундук заполняет `EditInventory`;
- `t_<Имя>` → текст окна сообщения (`t_Exit` — «Вы уверены, что хотите выйти?»).

Данные для скриптов — `program/data/pdm_screens.c` (`PdmScreens`):
- `.<экран>.title`/`.text` — номер и текст заголовка с `%s` («Магазин на %s» — остров города);
- `.<экран>.s.<S_ИМЯ>` — текст значения (`Ранг %d`, единица после числа);
- `.<экран>.list.<колонка>` — узел колонки списка;
- `.<экран>.t.<имя>` — тексты окон сообщений;
- `.goods.<stem>` / `.items.<stem>` — `name` и `about` из `TEXTS/RUSSIAN/GOODS/{GOODS,ITEMS}/<stem>.{nme,txt}` (cp1251). Товар находится по `PdmGoods.X.filename`, предмет — по `PdmItems.X.description`.

Груз корабля — `cargo.n<i>`, где `i` — номер товара в `PdmGoods`. Цены города и склад магазина появятся с торговлей (P9): пока цена оригинала стоит в обе стороны, а колонки склада и баланса пусты.

Секция, встреченная в двух файлах, получает суффикс файла: `messagebox_town`, `messagebox_ransack`. Кнопки с одинаковым прямоугольником (оригинал показывает одну из них по состоянию) — все, кроме первой, скрыты `bNotUse = 1`.

Пропуски выводятся в сводку: у `[Crew]` и `[Tavern]` нет фона (оригинал рисует их поверх сцены), куски рамок `frames\%s%d.tga` и `frames\decor\%s%d.tga` в установке отсутствуют.

Проверка: `SCENE=menu-newgame pdm-game/run.sh build/Debug/engine` — меню, через 6 с «Новая Игра» нажимается сама (`PostEvent`) и игра выходит в море. `SCENE=screens` показывает все экраны по очереди, затем F1 в городе.

## LOC — мир (`tools/pdm_world.py`)

Разобрано по `LoadLocatinFile` и `loadpoint` в `land_sector.dll`. Конвертер пишет модели локаций, патчи, всех персонажей `anim_types.idf` и `program/data/pdm_world.c` (`PdmLocations`, `PdmCharModels`). Скрипт `program/town.c` по этим данным ставит локацию, героя и NPC.

- Файл `.loc` — текст cp1251, строки разделены `\r\n` или `\n`.
- Заголовок: модель `.cff`, коллизия `Patch_*.cff`, камера `cam_twn`, вид звука (town, deadtown, sYard, store, tavern, taverns, thall, beltrop, cave — те же имена, что у `snd/*.snd`).
- У городов дальше 4 слота интерьеров: таверна, магазин, верфь, ратуша (`*_spa/_eng/_fra/_pir`, у пиратов вместо ратуши `beltrop`).
- Затем N точек по 12 строк: `type`, `x y z`, `ay`, угол прямоугольника, размер, ссылка (none / sea / street / имя слота).
- Типы точек:
  - 1 — выход, прямоугольник — дверь;
  - 4 — точка прибытия; герой появляется на той, чья ссылка — локация, откуда он пришёл. Она лежит внутри прямоугольника выхода, поэтому выход срабатывает только при входе в прямоугольник, а не при стоянии в нём;
  - 2 — солдаты;
  - 3, 9, 10 — гуляющие;
  - 5, 6, 7 — места у столов и стоек с диалогом;
  - 11 — трактирщик и сундук;
  - 12 — священник.
- Персонаж встаёт на свободную точку типа, равного классу его модели в `anim_types.idf`.
- Адрес персонажа: остров + номер локации:
  - 2 — улица, 3 — таверна, 4 — магазин, 5 — верфь, 6 — ратуша, 8 — солдаты;
  - остров с `_` в конце — мёртвая версия.
- Сюжет переносит персонажей строкой `Остров.вид` и пишет остров по-разному: «Gray Sails» при ключе `Gray_Sails`, «d'Orange» при `d_Orange`, «tendales». Сравнение идёт после нормализации: нижний регистр, `_` и `'` → пробел. `void` — персонаж убран из мира.
- Город острова берётся из поля `town` в `islands_x.idf`.
- Единица оригинала — 2,3 м (рост героя 0,78), города и персонажи масштабируются одинаково.

### Патч → `.ptc`

Оригинал проверяет точку по каждому треугольнику патча, поэтому патчи перекрываются: большой веер из одной вершины лежит поверх мелких треугольников площади. Движок Storm 2 ходит от треугольника к соседу через общее ребро, а ребро без соседа считает стеной. Поэтому `clean_patch` перестраивает патч:

1. Треугольник оставляет только ту часть, которую не накрыли **исходные** треугольники до него на том же уровне (разница высот меньше 0,4 м). Этажи дома и пролёты лестницы лежат друг над другом и сохраняются все. Вычитать нарезанные куски нельзя: каждый режет новый треугольник ещё на три, и патч HighRock из 217 треугольников разрастается до сотен тысяч щелей. Щели тоньше 1 мм отбрасываются.
2. Вершины сводятся к сетке 1 мм, у одной точки (x, z) может быть несколько уровней по высоте.
3. Вершина, лежащая на чужом ребре того же уровня, делит это ребро (без Т-стыков); многоугольник режется веером из центра.
4. Если на ребре сходятся больше двух треугольников (складка), лишние получают свою копию вершин чуть выше — там стена.

**Пол интерьеров.** В патче таверны есть галерея, лестница и стены от земли, но нет первого этажа: оригинал ходит по y = 0 внутри стен. Нижние кромки стен складываются в замкнутый контур, контур режется на треугольники ушами и идёт в патч последним (где у патча свой пол, остаётся он). Пол добавляется только в локациях без слотов интерьеров и только если внутри контура есть точка `.loc`, не покрытая патчем. В городе контуры — это дома.

**Препятствия.** Оригинал останавливает героя о геометрию модели локации. Движок Storm ходит только по патчу, а патчи PDM лежат под столами, лавками, бочками, телегами и углами домов: герой проходил сквозь них. `blocked_cells` делит пол на клетки 15 см. Клетка закрыта, если треугольник модели над ней (отсечённый по клетке) заходит в полосу тела 0,35–1,6 м над полом этой клетки. Высота берётся своя для каждого уровня, так что галерея не закрывает пол под собой. Закрытые клетки расширяются на одну (радиус тела) и сливаются в прямоугольники. `cut_obstacles` вычитает их из треугольников патча до `clean_patch`. Свободными остаются 0,45 м вокруг точек `.loc` (персонажи, места) и прямоугольники выходов, иначе дверной проём, нарисованный в модели, отрезал бы выход. Пересборка всех 44 патчей занимает около 6 минут.

### Персонажи (`tools/pdm_character.py`)

Персонаж оригинала — набор жёстких частей, у каждой ключ на кадр: перенос и поворот (Ry·Rx·Rz). Скелета в файле нет, но части движутся вместе: опора предплечья в каждом кадре стоит в одной точке плеча. Родитель части — та часть, в чьей системе её опора неподвижна. Дерево с наименьшей ошибкой строится алгоритмом Прима, корень — таз. Кость Storm = опора в системе родителя, поворот = R_родителя^T · R_части.

Действия берутся из `WORLDS/CHARACTERS/<anim>.idf`: имя, первый и последний кадр (если первый больше — проигрывается назад), скорость. Имена файлов в разном регистре (`Traktir_Man.idf`), поиск идёт без учёта регистра. Сидячие (drink, salor, hubernator) имеют только `do_some1..8` и `talk_1..12`. Скорость 30 у ходьбы героя даёт 0,031 единицы шага за кадр, отсюда частота оригинала — 10 кадров в секунду.

Проверка: `SCENE=town TOWN_AUTO=1 pdm-game/shots.sh build/Debug/engine <out> 75 …` — герой сам идёт от причала к таверне Granda Avilia, заходит и выходит обратно.

**Две сабли.** Клинок бойца (`soldier_spa_palash`, `pirat_sabel`) лежит в модели дважды: в ножнах на поясе и обнажённый в руке. Игра оригинала показывает одну копию по состоянию боя. Обнажённая копия глубже в дереве частей (висит на кисти), поясная — на тазе. Вне боя конвертер оставляет только поясную (`drawn_blades`).

## Тулбар моря и значок действия (`tools/pdm_hud.py`)

Оригинал рисует HUD моря из `SQUAD_CONTROL.dll` по картинкам `TEXTURES/toolbar/*.tga`:
- команды — `<имя>_n.tga` (обычная) и `<имя>_a.tga` (выбранная), 64×64; имена DLL: `town` — на землю, `map2` — карта, `time` — ускорение времени, `cancel` — отмена, `ocean` — в море, `followme`, `board`, `chase` и другие — бой (П4);
- картинки кораблей — `<icon>1.tga` (тёмная плашка) и `<icon>2.tga` (выбранный корабль); флаг нации — `tflag0..3.tga` (Англия, пираты, Франция, Испания), его голубой фон `(104,176,216)` — цветовой ключ;
- `ship_status.tga` — полосы парусов, экипажа и корпуса: сверху пустые, снизу полные.

Все картинки непрозрачные, рисунок занимает верхние 50 строк из 64, остальное — чистый чёрный `(0,0,0)`. Это цветовой ключ прозрачности: конвертер делает чёрный прозрачным, иначе под картинкой стоит чёрная полоса.

Выход (`resource/textures/battle_interface/pdm`):
- `commands.tga.tx` — сетка 8×4, команда i в ячейках 2i (обычная) и 2i+1 (выбранная);
- `ships.tga.tx` — сетка 16×16, ячейка `(icon·4 + флаг)·2 + выбран`. Сетка квадратная: движок берёт число строк из числа столбцов (`BIShipIcon::GetShipUVFromPictureIndex`);
- `status.tga.tx` и `back.tga.tx` — полосы и плашка под ними (у плашки полоса экипажа всегда полная: движок рисует только корпус и паруса);
- `program/data/pdm_hud.c` — `PdmHud`: ячейки команд, картинок и флагов, подписи команд и названия выходов из `[main]` `TEXTS/RUSSIAN/INI/interface.ini` (`land`, `sea_map`, `ControlTurboMode`, `tavern`, `sea` …).

Скрипт (`program/hud.c`) ставит их в `BATTLE_INTERFACE` (картинка корабля, полосы, меню команд по Tab) и в `ILogAndActions` (значок действия справа сверху, на море — «На землю» у гавани, на суше — выход, в котором стоит герой).

### Навигатор

Навигатор моря оригинала — `NAVIGATOR.dll` (строки DLL: `toolbar\compas-new.tf`, `obrooch4.tf`, `baba.tf`, `baba_niz.tf`, `wind.tf`, `guns_status.tf`, `guns_info.tf`, `object_land.tf`, `enemy_select.tf`, `selection2.tf`):
- `obrooch4.tga` / `.tf` — рамка 128×128 с альфой: кольцо (внешний радиус 64, внутренний около 58) и плашка внизу (строки 112–128);
- `compas-new.tf` — буквы N/E/S/W и ромбы между ними на радиусе 47–60, с альфой;
- `wind.tf` — синяя стрелка ветра на чёрном фоне через весь диаметр 128, к середине темнеет;
- `object_*.tf` — иглы кораблей 32×32: в `object_black` красная, в `object_red` зелёная (имена не совпадают с цветом);
- `baba.tf` / `baba_niz.tf` — контуры секторов огня борта и кормы, `guns_*` — отдельная панель пушек (П4).

`.tf` читает `tf_image` из `tools/tf2tx.py`. Выход:
- `nav_frame.tga.tx` — рамка, `nav_compass.tga.tx` — буквы компаса. Обе 256×256, картинка 128 увеличена до 192 в центре: квадрат навигатора общий для всех текстур (`navigatorWidth`), а полосе пушек нужно место снаружи кольца;
- `nav_cannons.tga.tx` — белое кольцо радиусом 98–110 из 256 (ours): движок вырезает из него дуги бортов и красит по перезарядке. Пока у корабля нет `Cannons.Borts` (П4), углы дуг нулевые: без этих атрибутов движок рисует дуги от угла 0, получается замкнутое кольцо;
- `nav_wind.tga.tx` — стрелка, альфа — утроенная яркость (чёрный фон прозрачный, тёмная середина видна на карте);
- `PdmHud.nav_scale` = 256/192 — во сколько раз квадрат навигатора больше рамки.

Движок поворачивает стрелку на угол «ветер − курс», а `whf_wind_angle` — направление, куда дует ветер (парус берёт вектор `(sin, cos)`). Поэтому остриё `wind.tf` (вверху) показывает, куда дует ветер.

## Звук и музыка (`tools/pdm_sound.py`)

Оригинал играет звуки по алиасам (`ENGINE.exe`: `Resource\Sounds\%s.wav`, `%s%d.wav`, `Resource\Music\%s.mp3`):
- `MUSIC/mmusic.ini` — `алиас,файл`. Файл — MP3 в обёртке RIFF WAVE (формат 0x55). Конвертер оставляет только чанк `data`, получается обычный `.mp3`.
- `SOUNDS/msound.ini` — `алиас,файл,число`. При числе больше 1 звук выбирается случайно из `файл0.wav … файлN-1.wav`. Файлы могут лежать в подпапках (`Witch\fon`), регистр имён любой.
- `WORLDS/nations.idf` — у нации `town_music`: алиас музыки её городов (`eTown`, `sTown`, `fTown`, `pTown`). Нация города — `PdmIslands.<остров>.nation`, индекс в `nations.idf`.
- `WORLDS/locations/snd/<вид>.snd` — 14 строк (описаны в `format`), вид звука берётся из строки `.loc`:
  1. шаги героя L/R;
  2. шаги мужчины L/R;
  3. шаги женщины L/R;
  4. фоновая петля днём и ночью;
  5. периодический звук днём и его интервал в мс;
  6. то же ночью;
  7. голос одного (`Single`) и голоса многих (`Many`).
  
  `null` означает «нет звука»; в `DeadTown.snd` опечатка `nill`.

Что пишется:
- `resource/sounds/pdm/**.wav` — звуки, на которые ссылаются алиасы, имена в нижнем регистре;
- `resource/sounds/pdm/music/*.mp3` — музыка без обёртки;
- `resource/ini/aliases/pdm.ini` — алиасы (сервис ищет их с учётом регистра, поэтому всё в нижнем регистре);
- `resource/ini/sound_scheme.ini` — `pdm_<вид>_day`/`_night`: периодический звук с паузой от половины до полутора интервалов и голос одного раз в 4–12 с;
- `program/data/pdm_sound.c` — `PdmMusic.<алиас>` и `PdmLocSounds.<вид>`.

`program/sound.c` играет одну музыку с плавной сменой: меню — `Main`, море — `Freesailing`, город — `town_music` нации острова. В локации запускаются петля дня (зацикленный стерео-звук, останавливается по id), голоса многих, если в локации больше двух персонажей, и схема.

**Шаги.** Их играет сама сущность персонажа движка (`character.cpp`, `PlayStep`):
- по событиям `LStep`/`RStep` действия в `.ani` она проигрывает 3D-алиас `step_<пол>` (при беге — `run_<пол>`);
- пол берётся из материала треугольника патча `snd_<пол>`; без материала используется `step_grass`.

Как это сделано для оригинала:
- `pdm_world.py` даёт патчу материал по шагам героя из `.snd` его локации:
  - `man_gsl` → `snd_ground`;
  - `man_woodstepl` → `snd_wood`;
  - `CrpStpl` → `snd_carpet`;
  - `CStepl` → `snd_stone`;
- `pdm_sound.py` пишет алиасы `step_`/`run_<пол>` из звуков левой и правой ноги;
- `pdm_character.py` ставит события шагов в `walk`/`run` на два кадра цикла, где таз ниже всего: в этот момент нога встаёт на землю. Отдельных шагов оригинала для мужчин и женщин (`mgsl`, `ggsl`) движок не различает, всем персонажам достаются шаги героя.

## Логика игры — в DLL

В `MODULES/` 104 модуля Storm 1 (PE32 i386). Каждый экспортирует только `?CreateEntity@@YAPAVEntity@@PAD@Z`. Скриптов на C, как в Storm 2, нет. Логика — это DLL плюс данные: ACTIONS, QUESTS, DIALOGS (сюжетная машина описана выше в разделе QL). Поэтому скрипты TEHO оригинал не запустят — нужен свой `program/*.c`, который читает данные PDM.

Декомпиляция: `GHIDRA=<ghidra> tools/ghidra/decompile.sh <out> MODULES/*.dll` (Ghidra 12.1.4 headless + `DumpDecomp.java`) выгружает C всех функций и строки в `<out>/<dll>.c` и `.strings.txt`. Результат декомпиляции в git не кладём: это код Akella.
